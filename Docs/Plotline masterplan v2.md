**Date:** 2026-09-24 (rev 2.1: tool/license model, $0 budget) · **Supersedes:** v1 and v2.0 · **Owner:** Shagor
**Pressure-tested:** two council rounds on strategy + one on the build decisions.

## 1. What Plotline is, in one paragraph

Plotline is the **digital show flat**. A developer pre-sells apartments off paper brochures and, at best, one physical show flat covering one unit type. With Plotline, the developer's own marketing/sales team loads a unit's floor plan, traces it in minutes (typing the dimensions the architect already printed on the plan — "14'-5" × 14'-4"" — so walls size themselves), and publishes a furnished 3D walkthrough that opens **in any phone browser** from a WhatsApp link. Buyers walk the actual unit, pick finishes from developer-approved options with taka price deltas, and tap anything to ask a question or request a change. Every choice and request lands in a **change list** both sides keep. The walkthrough sells the flat; the change list — a trusted written record in a market where "the tiles will be like the sample, inshallah" is a running joke — becomes the moat.

## 2. Who pays, and the two pitches

**Customer:** mid-tier Dhaka developers (REHAB ~930 member firms; the middle has money, unsold flats, and nothing better than static renders). **Signer:** head of sales/marketing. **Daily user & real decider:** the sales-office staffer — if it lags on a cheap tablet in front of a buyer, it dies in a drawer. **End users:** local buyers in the office; NRB buyers abroad, buying sight-unseen through relatives.

Pitch 1 (domestic): *"A show flat for every unit type, at 1% of the cost of building one — made by your own team in an afternoon."*
Pitch 2 (headline): *"Close your NRB leads without a site visit."* Track "% of link opens outside Bangladesh" from day one.

**The look problem, honestly:** agencies sell photoreal static renders ($100–300 each). Plotline won't out-pretty them and doesn't try: *"That render is a stock fantasy. This is YOUR flat — your layout, your sizes, your afternoon sunlight, on your phone."* Sell alongside renders, not against them. For the sight-unseen NRB buyer, accuracy beats gloss; for walk-ins, the render wins the first ten seconds — the staffer needs both.

**The adoption risk this model creates (the one to respect):** a tool means the CUSTOMER does the work. If tracing a unit takes their staff a frustrating day, they stop. Two mitigations are therefore core product, not polish: (a) **dimension-driven tracing** — click a corner, type the printed length, done in ~15 minutes per unit; (b) **white-glove pilots** — for the first 2–3 customers the founder personally drives the tool sitting with their team. That's onboarding and QA, not a service business.

## 3. Money ($0 spent before revenue)

- **Pricing hypotheses (the first 10 conversations set the real card):**
  - **Per-tower license:** all unit types, buyer links, sales-office mode — BDT 50k–1.5 lakh one-off + a yearly renewal (~25%) for hosting/support. One-off fits how BD developers budget (per-project), and avoids the slow MD approval that recurring fees trigger.
  - **Or monthly:** BDT 8–15k/month per active project, for developers who prefer small payments.
  - **Pilot deal for the first 2–3:** steep discount, paid (never free — free pilots produce polite lies), founder-driven onboarding, case-study rights.
- **Rules:** 50% upfront, always. Service pauses on non-payment.
- **Costs until revenue: effectively zero.** VS Code, Git/GitHub, TypeScript, React, Vite, Three.js: free. Supabase free tier, Vercel free tier (free .vercel.app URL), CC0 assets. Claude is the only paid tool. Trade license / bank / bKash paperwork starts only when a pilot gives a verbal yes.
- **Hooks wired now, sold later:** finish options stored as `brand + SKU + price` (paint/tile brands pay for catalog slots later); every buyer selection logged with timestamps ("73% picked the premium kitchen" — retention data for free).

## 4. What we build, in order

**Phase 0 — the pitch demo (week 1, all code).** One real unit, hardcoded as a data file (coordinates derived from the plan's printed dimensions — Claude Code drafts the JSON from the plan image, founder corrects), run through the generator, furnished from presets, deployed to a free public URL. No editors yet — one apartment doesn't need a factory.

**Phase A — the Studio + buyer link (weeks 2–6).** This is the product now, so the tracing editor is promoted from "internal tool" to core: load plan image, set scale, click corners, **type printed dimensions to size walls**, snapping, mark doors/windows with widths, wall thickness; generate; furnish via per-room presets; publish. Buyer link: Bangla/English, walk + tap-to-move, finish options with taka deltas, object-anchored comments, compass + sun position ("where does the sun hit the balcony at Asr" — no static render can answer that), floor number, per-sqft math, a **"share this exact configured version"** button (the NRB buyer decides with his brother — the configuration must travel).

**Phase B — sales-office mode + change list (months 2–3).** Staff-driven demo mode, preloaded/offline-capable for load-shedding; change-list PDF export the developer can annex to the sale agreement (a shared record, not a legal instrument, until a lawyer validates it); buyer's own copy via WhatsApp/email; simple furniture-arranging UI for customers (until then: presets + config file, hand-tweaked during white-glove pilots).

**Phase C — leverage (month 3+, revenue-funded).** Template library (Dhaka layouts repeat — the 10th similar unit costs minutes); whole-tower parameterization (floor/orientation variants from one trace); **AI-assisted import**: read the plan's printed room labels and dimensions (tractable) rather than detecting walls pixel-by-pixel (research problem) — "AI drafts, human confirms." Self-serve onboarding so pilots stop needing the founder in the room.

**Not building in the first 6 weeks:** drag-and-drop furniture placement editor (presets + config file instead), pixel-based floor-plan auto-detection, buyer geometry editing, VR, photorealism, cost-estimation engine, payments integration, native apps.

## 5. How the technology works (plain language)

**Pipeline:** printed-dimension tracing → **wall graph** → generated 3D → preset furnishing → published link.

The **wall graph** is the core data structure and the fix for the old prototype's broken doors: corners → wall segments between corners (one wall shared by two rooms) → doors/windows as children of a wall ("1.2m along, 0.9m wide") → rooms *derived* as the enclosed spaces. Walls are arbitrary-angle from day one — real plans have chamfered corners, stepped verandas, thick shear walls, lift cores, AOD shafts.

**Stack (all free, all hiring-standard):** **TypeScript** (JavaScript with type-checking — catches mistakes before they run) · **React** (the standard UI library) · **Three.js** (browser 3D engine, current release) · **Vite** (build + instant reload) · **Supabase** (backend-in-a-box: Postgres database, sign-in links, storage; its **RLS** row-level-security rules keep one developer's data invisible to another — the change list holds buyer phone numbers and negotiated prices, so RLS is tested with two fake tenants before any real data) · **Vercel** (push code, get a live URL).

**Furniture:** one curated kit (~30 models, ONE consistent style, licenses individually verified — free marketplaces mislabel stolen assets; every asset recorded in a manifest). Rooms furnished by presets ("bedroom set against the longest wall"), tweaked per unit.

**Performance budget (a launch gate, not polish):** opens < 8s on a 3-year-old Android over 4G, < 5MB initial, ~30fps, < 100 draw calls (merge meshes, Draco/KTX2 compression, shared texture atlas). Test on a real cheap Android weekly — AI-generated 3D code "works on the laptop" and dies on the phone silently.

## 6. How we get customers

Week 1–2: **discovery demos, not sales calls** — show the deployed link to 3 developer-connected contacts (relatives, classmates, interior designers who serve developers) and watch what they do. Their reactions steer weeks 2–6. Then: pilot pitches to sales heads (visit as a prospective buyer first, watch how they sell); one **lighthouse** developer at a discount for a case study and REHAB-fair co-presence; every buyer link footed "Powered by Plotline" so links travel WhatsApp diaspora networks for free.

## 8. Working rules (what keeps a solo vibe-coding founder alive)

Small commits, feature branches, never code on main, read every diff before accepting. CLAUDE.md in the repo carries the invariants. Vitest tests on the wall-graph core only. Plan mode before geometry work. RLS two-tenant test before any real buyer data. Weekly: cheap-Android test, off-site backup, metrics row.

## 9. Risks and fixes

"Looks like a video game" → one coherent kit + the your-actual-flat framing + sell alongside renders. Real plans break the generator → arbitrary-angle graph, curves as segments, columns as objects. **Customer won't do the tracing work** (the new #1 risk) → dimension-driven tracing under 15 min/unit, white-glove pilots, and templates so repeat layouts are near-free; if pilots show staff simply won't trace, the fallback inside the model is founder-does-tracing as paid onboarding — contained, temporary. Cheap phones choke → §5 budget enforced weekly. Stolen "free" assets → license manifest. Data leaks → RLS tests. Slow payments → 50% upfront, pause on non-payment. Copycats → speed, whole-tower coverage, NRB story, lighthouse lock-in. Bus factor → docs + backups.

## 10. Numbers we watch weekly

Discovery demos/pitches · paid pilots · **cash collected** · minutes to trace a unit (the adoption number) · links sent vs opened (>30%) · % opens outside Bangladesh · links forwarded per buyer · staff-driven sessions · options selected · change requests · buyer-copy opens.

## 11. What kills this that we cannot fix

If Dhaka sales heads won't pay for digital sales tools at any price, no feature fixes it — only the week-6 gate detects it. And if their staff won't trace plans even at 15 minutes a unit, the tool model specifically fails and the gate catches that too. **Build fast, show early, let paid pilots decide.**

## Glossary

**glTF** — standard web 3D model format (JPG for 3D). **CC0** — free-for-any-use license; verify per file. **Procedural generation** — 3D built by code from data. **Wall graph** — corners → shared wall segments → openings on walls → rooms derived. **PBR** — materials defined by physical properties so light behaves right. **Draw call** — one instruction to the graphics chip; too many = lag. **Draco/KTX2** — 3D/texture compression. **Texture atlas** — many images packed into one file. **Supabase/Postgres/RLS** — backend-in-a-box / its database / per-row access rules. **TypeScript/React/Vite/Three.js/Vercel** — typed JS / UI library / build tool / 3D engine / push-to-deploy hosting. **Repo** — the Git-tracked code folder. **NRB** — non-resident Bangladeshi. **White-glove pilot** — a paid early customer you personally onboard and operate for, to learn and to close.
